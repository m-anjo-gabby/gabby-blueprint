# 置き方・書き方の決まり

## 正本と置き場所

- 仕様・テストの正本はリポジトリ（`docs/`・`testing/`）。共有ドライブには、リポジトリから作った読み物を置く。共有ドライブ側の内容をリポジトリへ書き戻す仕組みは作らない。
- ルートは見る人で分ける: A_開発（開発チーム）／B_運営共有（運営スタッフ）／C_教材制作（コンテンツチームと開発チーム。教材データ・CV辞書の受け渡し）。中は資料の種類で分ける。
- 開発チームの下書き・検討は A_開発、運営スタッフに見せる完成品は B_運営共有に置く。下書きを B に置かない。運営に書き込んでもらう確認の一覧は B に置く（A は運営が開けない）。
- アプリの文言（メール・評価コメント等）の一覧と確認は B/60_アプリの文言 に題材ごとのフォルダで置く。教材のフォルダ（C）には入れない。
- アーティファクト・Claude Docs は下書きと確認に使う。運営スタッフに渡す完成品は B_運営共有に置く。

## 形式

| 種類 | 形式 | ファイル名 |
|---|---|---|
| 内容を更新し続ける資料（マニュアル・業務フロー・機能の説明・案内） | Googleドキュメント | 日付を付けない（例: `生徒の招待`） |
| その時点の控え（リリース情報・メール文面カタログ・提案） | PDF | `名前_YYYYMMDD.pdf`（例: `リリース情報_20261004_20261008.pdf`）。日付は末尾に付ける（先頭だと名前が見づらいため） |

- 日付は資料の基準日（リリース資料は対象期間の終わり、カタログは作った日）。
- 同じ名前の古い版は消さずに 90_アーカイブ へ移す（PDF は日付で区別できるため移さなくてよい）。

## 運営向けの資料に書かないもの

- 開発用の情報: RPC名・テーブル名・関数名・接続先のURL（dev/staging）・環境変数名。
- 認証情報・テスト用アカウントのパスワード。
- 利用者の個人情報（氏名・メールアドレス）。例を出す場合は架空の値にする。

## 文章

- 読み手は非エンジニアの運営スタッフ。画面での操作と結果で書き、内部の仕組みは書かない。
- アプリの呼び方は「生徒アプリ」「コーチアプリ」「管理画面」、製品名は「Gabby Blueprint」。
- 見出しはドキュメントの見出しスタイルで付け、箇条書きは記号を手で打たずリスト機能を使う。
