# リリース作業

手順の正本は [docs/RELEASE.md](../../../docs/RELEASE.md)。このスキルは、Claude が進め役になるときの分担・進め方と、
リリースごとの記録・改善の仕組み（[HISTORY.md](HISTORY.md)）を持つ。

## 始める前に

1. [docs/RELEASE.md](../../../docs/RELEASE.md) を読み、今どの段階か（staging / 本番、どの手順まで済んだか）をユーザーの依頼と照らす。
2. [HISTORY.md](HISTORY.md) の「つまずきと対処」を読み、同じ失敗を繰り返さない。
3. `pnpm release:status --env=<staging|prod>` で現状を確かめる（読み取りのみ。本番は一時トークンを環境変数で渡す）。
   対象のリリーススクリプトと、まとめて出す前のリリースが残っていないか（未適用のファイル）をここで確かめる。

## 分担

| 操作 | 誰が | 備考 |
|---|---|---|
| PR の作成・マージ | ユーザー | この環境には `gh` が無い。ブランチの push は Claude が行ってよい（依頼がある場合） |
| `release:status`・`run.mjs --status`・`schema.mjs --check`・`--list` | Claude | 読み取りのみ |
| dev への `run.mjs` | Claude | 確認なしで実行してよい（`echo y |` で確認に答える） |
| staging への `run.mjs` | Claude（ユーザーの明示の指示の後） | 1回目は自動モードの判定で止められることがある。止められたら回避せず、ユーザーに実行の指示を求める |
| 本番への `run.mjs` | ユーザー、またはユーザーが一時トークンを渡して指示した場合は Claude | トークンは `SUPABASE_ACCESS_TOKEN` 環境変数で渡す。Reference ID の確認は標準入力で答える |
| `pnpm vercel-env --apply`・値ファイルへのトークンの記入 | ユーザー | 自動モードでは秘密の書き込みが止められる |
| GitHub Actions の `Deploy` の実行 | ユーザー | 実行後に Claude が `release:status` で確かめる |
| Vercel のプロジェクト設定の変更 | ユーザーの指示がある場合だけ Claude | API で行い、変更後に読み直して確かめる |
| E2E（staging） | Claude | 対象を絞って実行する（docs/RELEASE.md の 2-6） |

- 外部に影響する操作（staging・本番の DB、Vercel の設定、データの削除）は、その都度ユーザーの指示があってから行う。前の段階での承認を次の段階へ持ち越さない。
- 実行結果は数字と状態で報告する（適用したセクション数、デプロイされたコミット、`release:status` の判定）。

## 進め方の注意

- 本番の `run.mjs` に標準入力で答える場合、トークンは環境変数で渡し、標準入力には Reference ID だけを渡す。
  トークンの入力欄とReference ID の確認を同じ入力から続けて答えると、1つ目の入力欄に2行とも読み込まれて確認で止まる。
- 複数のリリースをまとめて出す場合は、古いリリーススクリプトから順に適用する。
- リリーススクリプトの冒頭のコメントは、適用後に書き換えない（セクション1のハッシュが変わり「適用後に内容変更あり」になる）。手順の補足は docs/RELEASE.md に書く。
- 時間のかかるコマンド（E2E 等）は、最初の要約行（対象の件数）を確かめてから待つ。

## 終わったら（改善の仕組み）

リリースのたびに、最後に次を行う。

1. [HISTORY.md](HISTORY.md) の「リリースの記録」に1行足す（日付・ブランチ・環境・適用したスクリプト・デプロイしたコミット・確認結果）。
2. つまずいたこと・手間がかかったことがあれば「つまずきと対処」に足し、**同じタスクで**次のどれかに反映する。
   - 手順・確認項目の不足 → docs/RELEASE.md
   - 道具で防げるもの → `supabase/release/`・`scripts/vercel-env/`・`.github/workflows/deploy.yml` の改善
   - Claude の進め方 → このファイルの「分担」「進め方の注意」
3. 反映できなかったもの（大きい改善）は「改善の候補」に残し、ユーザーに一言伝える。
4. HISTORY.md を片付ける。前回までに反映済みで、今回起きなかったつまずきの行を消し、「リリースの記録」を直近10件にする。
