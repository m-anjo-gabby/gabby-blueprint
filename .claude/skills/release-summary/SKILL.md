# リリース向け変更概要資料

開発ブランチ1つ分の変更を、非エンジニア（運用担当・ステークホルダー）向けに1枚のHTMLページにまとめ、アーティファクトとして公開する。
毎回の指示のぶれをなくすため、書き方・構成・見た目はこのスキルのファイルを正本にする。

- 書き方・構成・チェックリスト: [reference/writing-rules.md](reference/writing-rules.md)（**書き始める前に必ず全部読む**。末尾の「改善ルール」を含む）
- 紙面のテンプレート: [reference/template.html](reference/template.html)（CSS はそのまま使う）
- 過去の資料と改善の記録: [HISTORY.md](HISTORY.md)
- 材料の集計: `scripts/collect.mjs`（リポジトリルートから実行）

## 手順

### 1. 対象と前提を確かめる

- 対象ブランチ（例: `feature/20261004-dev`）と、反映状況（dev のみ／検証環境にマージ済み／本番反映前 等）をユーザーの依頼から読み取る。分からなければ聞く。
- ユーザーが大きな変更点・品質施策を挙げている場合は、それを柱にする（挙げていない場合は材料から選び、柱にした理由を報告で一言添える）。
- [HISTORY.md](HISTORY.md) の直近の資料を Artifact の `read` で読み、前回からの続き（品質施策の「今後の進め方」で予告した内容など）を確認する。

### 2. 材料を集める

```bash
git fetch --all -q
node .claude/skills/release-summary/scripts/collect.mjs feature/YYYYMMDD-dev --out=<スクラッチパッド>/facts-YYYYMMDD.md
```

- 出力: コミット数・期間・領域ごとの変更数・ブラウザ自動テスト数の前後・仕様書の追加/更新・新規テーブル・リリーススクリプトの項目と冒頭（手作業の手順・環境変数）・各項目の【注意】・全コミットの本文。
- staging にまだマージしていない場合は `--base=<前回の staging のマージコミット>` を付ける。
- 表示文言・表示条件は、画面仕様書（`docs/screens/`）・機能仕様書（`testing/e2e/specs/`）・ソースで確かめる。メールや画面の見本を図にする場合は、実際の文言をテンプレート・コンポーネントから写す。

### 3. 構成を決める

writing-rules.md の「4. 構成」に沿って、柱（メイン2〜3個）・品質向上・その他・影響範囲（最大5つ）・リリース時の確認事項に振り分ける。
同じブランチの中で作って直したものは、最終的な姿だけを書く。

### 4. 書く

- テンプレートをスクラッチパッドに `release-summary-YYYYMMDD.html` としてコピーし、本文を書く。CSS は変えない（部品が足りない場合だけ足し、足した部品はテンプレートにも戻す）。
- 柱の仕組みが伝わりにくいものは、図（`flow`・`matrix`・画面やメールの見本）を1つ添える。飾りの図は入れない。
- `<title>` は柱を2つまで並べた短い名前（例: 「メール基盤＆グループセッション」）。

### 5. 確かめる

writing-rules.md の「6. 仕上げのチェック」を全部確かめる。数値は facts の出力と突き合わせる。

### 6. 配布用のPDFを作る

配布はPDFで行う（ブラウザの印刷機能は、アーティファクトの枠の中を印刷するため改ページが崩れる。使わない）。

```bash
node .claude/skills/release-summary/scripts/to-pdf.mjs <スクラッチパッド>/release-summary-YYYYMMDD.html
```

- A4・ライトの配色で、同じフォルダに `release-summary-YYYYMMDD.pdf` を出力する（ページ番号付き）。改ページの規則は template.html の `@media print` にある。
- 出力したPDFを Read で全ページ確かめ、次が無いことを確認する: 枠・表・項目の途中での改ページ、見出しや説明文だけがページ末尾に残る、文字の見切れ。直す場合は `@media print` を直し（template.html にも戻す）、出力し直す。確認は1回直したら終える。

### 7. 公開して記録する

- Artifact で公開する（`icon`: `document`、`description` は柱を1文で）。
- PDFのパスをユーザーに伝える（配布用）。
- [HISTORY.md](HISTORY.md) の一覧に、日付・ブランチ・URL・柱を1行足す。
- 報告では、資料の読み手（「運用担当・ステークホルダー向け」）、柱、推測や未確認の点（あれば）を短く伝え、気になる点があれば指摘してほしいと添える。

## 改善の手順（フィードバックを受けたとき）

資料の品質を回ごとに上げるため、指摘はその場の修正で終わらせず、必ずスキルに残す。

1. 指摘を資料に反映し、同じURLへ再公開する（同じファイルパスで publish）。
2. 指摘の種類に応じて、スキルのファイルを直す。
   - 書き方・用語・構成の指摘 → writing-rules.md 末尾の「改善ルール」に `- YYYY-MM-DD: 指摘 → ルール` を1行足す。
   - 見た目の指摘 → template.html の CSS / 骨組みを直す。
   - 手順・材料の不足 → この SKILL.md の手順、または collect.mjs を直す。
3. [HISTORY.md](HISTORY.md) の「改善の記録」に、何を直したかを1行足す。
4. 同じ指摘が2回出たら、改善ルールから writing-rules.md の本文へ格上げする（ルールの置き場所を1か所にする）。
