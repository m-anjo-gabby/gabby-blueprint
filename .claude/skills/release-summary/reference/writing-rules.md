# 変更概要資料の書き方（正本）

資料を書く前に必ず全体を読む。末尾の「改善ルール」は過去の指摘から足したもので、上の本文と食い違う場合は改善ルールを優先する。

## 1. 読み手と目的

- 読み手: 運用担当者（運営スタッフ・サポート）とステークホルダー（経営・営業・顧客企業の窓口担当）。**エンジニアではない**。
- 目的は3つ。上から順に大事。
  1. **誰に何が起きるか**が分かる（生徒・コーチ・運営・顧客企業のご担当者、それぞれ何が変わるか）。
  2. **リリースの前後に運用側がやること**が分かる（周知・設定・問い合わせ対応）。
  3. 開発の取り組み（品質向上など）が伝わる。
- 1回読めば分かることを優先し、網羅性は二の次にする。読み手が気にしない内部の作り替え（リファクタリング・型・関数名の整理）は、まとめて1行にするか「その他」に回すか、省く。

## 2. 言葉づかい

- 文体は「です・ます」。主語は利用者側（「〜できるようにしました」「〜が届きます」）。
- 画面の名前・ボタンの文言は、**アプリに実際に表示される日本語**で書く（コーチアプリは英語表示なので、英語の文言を「」で括って書いてよい）。ソースや仕様書（`docs/screens/`）で表記を確かめる。
- 技術用語は使わない。どうしても要る場合は、初出で「何のためのものか」を一言添える。よく出る言い換え:

| 書かない | 書く |
|---|---|
| RPC / 関数 / トリガー / テーブル | 仕組み・データベース（数を示すときだけ「DB変更の項目」） |
| E2E / Playwright のテスト | ブラウザ自動テスト（ブラウザを自動で操作して画面の動きを確かめるテスト） |
| 単体テスト | 画面を使わずに確かめる、より速いテスト |
| 仕様書（docs/screens 等） | 画面仕様書・機能仕様書 |
| リファクタリング | 内部の整理（見た目・動作は変わりません） |
| デプロイ | アプリの公開 |
| マイグレーション / リリーススクリプトの適用 | DBの変更の適用 |
| 環境変数 | アプリの設定値（反映作業者向けの欄では「環境変数」も可） |
| pg_cron / ジョブ | 定期的に動く処理（5分ごと・毎日 9:00 など、頻度で書く） |
| Webhook | メールの到達状況の受け取り |
| UTC・タイムゾーンの内部処理 | 「生徒から見た時刻」「コーチ側の夏時間」など、利用者が体験する言葉で |
| staging / 本番 | 検証環境 / 本番環境 |

- ファイル名・コマンド・変数名は、末尾の「リリース時の確認事項」の反映作業の欄にだけ書いてよい（`mono` クラスで等幅にする）。
- 数字は具体的に（「24時間前と1時間前」「14日ごと」「最大半年」）。「多数」「大幅に」などのぼかしは使わない。
- 不具合の修正は、**何が起きていたか → どうなったか**の順で書く。利用者に影響が無かったものは「画面に表示されることはありませんでした」のように明記する。
- 個人情報（実在の生徒・コーチ・顧客の名前、メールアドレス）は書かない。顧客名が要る場合は「顧客A」等にする。開発メールアドレスはフッターだけ。

## 3. 項目の区分（タグ）

| タグ | 使う場面 |
|---|---|
| `new` 新機能 | 利用者ができることが増えた |
| `improve` 改善 | 既存の機能の使い勝手・表示・速度・文言が良くなった |
| `fix` 修正 | 意図と違う動きを直した |
| `new` 新規（品質の節だけ） | テスト・仕様書を新たに作った |

- セクションの見出しバッジ: 今回の中心は「メイン」（緑）、品質向上は「品質向上施策」（藍）。メインは2〜3個まで。
- 運用上の注意は、各セクション末尾の `callout`（🧾 運用上のポイント / ⚠️ 注意）に書く。本文に紛れ込ませない。

## 4. 構成（この順番で書く）

1. **見出し（masthead）**: 1行の題（今回の柱を2つまで）、2〜3文の概要、ブランチ・期間・対象アプリのチップ。
2. **この更新について（lede）**: 背景（なぜ作ったか）→ 何をしたか、を1段落で。柱ごとに太字。
3. **影響範囲（risk-banner）**: 既存の利用者に見える変化・運用が変わる点を最大5つ。「何もしなくても困らない変更」は載せない。影響が小さい回は「見た目は変わりません」と明言する。
4. **数値（stats）**: 4つ。対象コミット数・ブラウザ自動テスト数・その回を象徴する数（例: 翻訳した文言数、新たに送るメールの種類）・DB変更の項目数。数値は `scripts/collect.mjs` の出力から取り、推測しない。
5. **目次（index）**: メインは `main`、品質は `quality` クラス。最後に「リリース時の確認事項」。
6. **メインのセクション**: 1つの柱につき1セクション。`section-intro` で対象アプリと「誰に関係するか」を書き、仕組みの流れが要るものは `flow`（3ステップ）や図解（実際の画面・メールの構成を模したもの）で示す。項目はアプリ別または利用場面別に `h3` で分ける。
7. **品質向上のセクション**: `q-grid` の3つの数字 → 何を確かめられるようになったか → 「今後の進め方」。毎回「アプリの見た目や動作に変化はありません」に相当する一文を入れる（該当する場合）。前回からの続きであることが分かるように書く（前回の資料を読んで確認する）。
8. **その他のセクション**: 小さな改善は `misc` の表（項目・内容・対象）にまとめる。対象は「生徒 / コーチ / 管理者 / 全アプリ / 開発・反映作業」。
9. **リリース時の確認事項（ops）**: `h3` で「反映作業」「関係者への周知」に分ける。反映作業は手順順、周知は相手（生徒・コーチ・運営スタッフ・顧客企業）ごと。順番を守らないと壊れる作業は `<strong>` で強調する。
10. **フッター**: `prepared by Blueprint開発サポート` と開発メールアドレス。

## 5. 事実の確かめ方

- 根拠は「コミットの本文」「リリーススクリプトの冒頭と各セクションの【注意】」「画面仕様書（`docs/screens/`）」「機能仕様書（`testing/e2e/specs/`）」。記憶や推測で書かない。
- 表示文言・条件（誰に出るか・いつ出るか）は仕様書かソースで確かめる。コミットの途中で文言が変わっていることが多い（最後のコミットの状態を書く）。
- 1つのブランチの中で「作って→直した」ものは、最終的な姿だけを書く（途中経過は書かない）。
- 運用に効く例外（例: 管理者の操作では通知しない、ライセンスの無い生徒には送らない）は漏らさず書く。
- 反映状況（dev のみ・検証環境に反映済み等）は、ユーザーの説明と `supabase/release/` の記載を突き合わせ、分からなければ書かないか、ユーザーに確かめる。

## 6. 仕上げのチェック（公開前に全部確かめる）

- [ ] 技術用語の言い換え表に載っている言葉が、反映作業の欄以外に残っていない
- [ ] 英語の大文字ラベル・アルファベットの略語を、説明なしに使っていない
- [ ] 数値が `collect.mjs` の出力と一致している
- [ ] 影響範囲（risk-banner）の各項目が、「関係者への周知」に対応する行を持っている
- [ ] DB変更とアプリ公開の順番の制約が、反映作業に書かれている
- [ ] 画面・ボタンの名前がアプリの表示と一致している
- [ ] スマホ幅（400px）で横スクロールしない・ダークモードで読める
- [ ] PDF（`scripts/to-pdf.mjs`）で、枠・表の途中の改ページや、見出しだけがページ末尾に残る箇所が無い
- [ ] `<title>` は短い名前（今回の柱を2つまで並べる。例: 「メール基盤＆グループセッション」）
