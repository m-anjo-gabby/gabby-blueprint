# テスト判断基準ガイド(TEST-JUDGEMENT-GUIDE)

テスト・調査で得た気づき（失敗・非自明な挙動・実装と仕様書の齟齬）を、次の作業で同じ失敗をしないための判断基準に育てる場所。
技術ルールの正本は [CONVENTIONS.md](./CONVENTIONS.md)（データ主体テスト）・[e2e/CONVENTIONS.md](./e2e/CONVENTIONS.md)（E2E）・[FIXTURES.md](./FIXTURES.md)（アカウント・データ）。

## 読み方

- テストに着手する時は、1章の判断基準のうち作業に関係する分類だけを読む。2章の事例は、判断基準から KJ 番号で引く（全部は読まない）。
- 判断に迷ったら、同じ分類の事例を読む。

## 気づきの育て方（記録 → 昇格 → 片付け）

1. **記録**: 新しい気づきは、2章の該当する分類の末尾に事例（KJ）を足し、1章の同じ分類に判断基準を1行で足す（既存の行で足りれば KJ 番号だけ足す）。
   `testing/e2e/specs/`・`docs/screens/` の作業で見つけた齟齬もここに記録し、仕様書はその場で今の形に直す（仕様書には経緯を書かない）。
2. **昇格**: 記録する時に、より強い置き場へ移せないかを先に考える。強い順に:
   1. 仕組み（ヘルパー・単体テスト・preflight・残骸の確認・lint）で機械的に止める
   2. 規約（`CONVENTIONS.md`・`e2e/CONVENTIONS.md`・`FIXTURES.md`）に今の決まりとして書く
   3. 1章の判断基準に書き、事例を2章に残す

   1・2 に移した事例は2章から消す（経緯は git の履歴にある）。「記録しただけでは同じ失敗を繰り返す」ため、同じ失敗が2回起きた教訓は 1 か 2 へ移す。
3. **片付け**: 事例を足す時に同じ分類の事例を見直し、原因が無くなった（不具合を直した・関数を廃止した）もの、判断基準・規約に吸収されたもの、同じ教訓のものをまとめて消す。
   ファイル全体が600行を超えたら、全分類を棚卸しする。

他のファイル・コードのコメントから参照されている KJ 番号は、消す時に参照元も直す（`grep -rn "KJ-<番号>"`）。
参照切れ・判断基準が指す事例の有無・行数（600行）は単体テスト（`testing/unit/judgement-guide.test.ts`）で検査する。

### 記入フォーマット

```
### KJ-<YYYY>-<MMDD>-<連番> <短いタイトル>

- **場面**: 該当シナリオ・仕様書・テストのパス（環境・日付）
- **事象**: 何が起きたか
- **原因**: なぜ起きたか
- **対処**: どう直したか（任意）
- **教訓**: この事例から一般化できる判断基準
```

## 1. 判断基準

### 1-1. リリース・DB の反映の確認

- preflight（`assertReleaseApplied`）は「関数があり、シグネチャが合う」ことしか保証しない。関数の本体の不具合、内部で呼ぶ別の関数の未反映、CHECK 制約の変更は検出できない。内部で呼ぶ関数も確認の対象に入れ、正常完了の経路を通すテストを必ず1つ含める（KJ-2026-0917-01・KJ-2026-0914-01）。
- 関数が「無いこと」の確認は `assertRpcRemoved` を使う（`42883` と PostgREST の `PGRST202` の両方を「無い」と判定する。`testing/helpers/preflight.ts`）。
- 複数段階の更新をする RPC は、一部だけ未反映でもエラーにならず部分的に成功する。状態と集計値（`used_sessions` と実際の件数等）を突き合わせる（KJ-2026-0904-01）。
- dev で通った検証が staging で落ちたら、まず staging だけの未反映を疑う。欠けた関数をテストから再適用せず、利用者に報告する（KJ-2026-0917-01）。
- `run.mjs --status` の「記録のみ」は DB に反映済みの証明ではない。想定外の制約違反・未定義の関数が出たらカタログ（`pg_constraint`・`pg_proc`）を直接見る（KJ-2026-0924-04）。
- 制約を足すセクションは、過去のテストデータの違反で staging の適用が止まることがある。本番の適用の前に、同じ条件の読み取りで本番のデータも確かめる（KJ-2026-0924-01）。

### 1-2. DB の関数・制約の落とし穴

- PL/pgSQL で他の関数を位置引数で呼ぶ時、smallint 等の引数に裸の整数リテラルを渡さない（`5::smallint` と書く）。「関数はあるのに does not exist」は、プーラーを疑う前に引数の型を確かめる（KJ-2026-0917-05）。
- 一意インデックスを部分インデックス（WHERE 付き）に変えたら、それを使う `ON CONFLICT` を全て探して同じ WHERE を付ける（KJ-2026-0914-01）。
- ビューの列を増減したら、そのビューを戻り値にする関数（`RETURNS SETOF <ビュー>`）を探して実際に呼ぶ。新しい RPC は `RETURNS TABLE (...)` で列を明示する（KJ-2026-0930-04）。
- 関数の中で「状態を更新してから例外」にすると、更新も取り消される。仕様書のこの種の記述は実際の動きで確かめる（KJ-2026-1010-01）。
- DATE の期間と timestamptz の列を比べる処理は、日本時間の月初開始・月末終了のデータで、境界の前後の月を必ず確かめる（片側だけずれるため、中間の月では気づけない）。
- NOT NULL の列を足すと、そのテーブルへ直接 INSERT するテストのスクリプトが実行時に壊れる（preflight では分からない）。古いスクリプトを再実行する前に直接 INSERT の箇所を確かめる。

### 1-3. テストデータの作り方

- 「過去の実績」と「今後の予定」を分けて作る。過去の実績は service_role で直接作ってから本物の RPC（実際のロールの JWT）で状態を進め、今後の予定は本物の RPC で作る（KJ-2026-0910-01）。
- 直接 INSERT するデータも業務ルール（同じ生徒の有効なライセンスは期間が重ならない等）に従う。後から制約を足すリリースを止める原因になる（KJ-2026-0924-01）。
- 集計・通算のテーブルは、本番と同じ RPC・トリガーを通さないと整合しない。通算値を確かめるテストは本物の RPC で実績を作る（KJ-2026-0926-03）。
- 制約を1つだけ確かめるテストは、他の制約（UNIQUE 等）や被験者自身の既存データに触れない値を選ぶ。テーブルの制約の検証は service_role の直接操作でよい（KJ-2026-0923-01）。
- 固定アカウントのロール・所属は投入スクリプト（`seed-fixed-accounts.ts`）で付ける。手作業で付けると環境ごとに食い違う。古い使い捨てアカウントを固定アカウントに転用しない（KJ-2026-1001-01）。
- 件数の検証が期待より**多い**時は、以前の実行の残骸（孤立データ）を疑う。少ない・0件の時は機能の不具合を疑う。
- 過去の使い捨てデータの一括削除は、命名で機械的に対象を決め、「対象外とまたぐデータ」があれば中止する安全装置を付け、例外で終わる dry-run を先に流す（KJ-2026-0924-03）。

### 1-4. 呼び出し方・テストの書き方

- 業務の RPC は実際にサインインしたロールの JWT で呼ぶ（`CONVENTIONS.md` 3章）。
- RPC の引数を足す・名前を変える時は、`testing/` 全体を grep して、過去の世代の書き方も含めて全ての呼び出しを直す。デフォルト引数の追加は型検査を通ったまま別の分岐に倒れる（KJ-2026-0915-02）。
- `revalidatePath` を使うサーバーアクションは、tsx からの直接の import では完走しない。DB への書き込みの確認なら、戻り値ではなく前後の DB の値で判定する（KJ-2026-0923-02）。
- `import 'server-only'` の付いた共通モジュールはテストから import しない（KJ-2026-0930-01）。
- 文面・判定を変えない整理（リファクタ）は、組み立て処理を全パターン実行して前後の出力が1文字も変わらないことを完了条件にする（KJ-2026-1006-02）。
- 状態を戻すべき操作を楽観的に表示する部品は、戻り値の失敗と例外（通信の失敗）の両方で元に戻ることを確かめる（KJ-2026-1013-02）。
- 認証の失敗等の文言は表示言語で変わる。分岐は `errorCode` で行い、テストは表示欄の有無を主に確かめる（admin は言語の Cookie が無いと英語になる）。

### 1-5. E2E の待ち方・取り方

- ハイドレーション・骨組み・Realtime・楽観的な表示・CAPTCHA の待ち方は `e2e/CONVENTIONS.md` 9章。固定の待ち時間で解決しない（KJ-2026-0928-02・KJ-2026-1018-01）。
- 「押しても何も起きない」時、通信が起きていなければハイドレーション待ち、通信が起きて表示が変わらなければ描画の不具合を疑う（KJ-2026-1017-01）。
- 開いた時の通信の回数は、直接開く場合（レイアウトの初期データとの競争で変わる）と画面内の移動で開く場合を分けて数える（KJ-2026-1018-02）。
- ロールで取得できなくなったら、まずモーダル（背後を `aria-hidden` にする）が開いていないかを `error-context.md` で確かめる。
- admin の検索式セレクト（`SearchableSelect`）は契約・一括登録のダイアログでラベルと関連付いておらず、名前で取得できない。ダイアログ内の順番で取る。

### 1-6. E2E の実行・環境

- 実行・絞り込み・staging での実行は `e2e/CONVENTIONS.md` 7章、後始末は10章。
- テストが初回だけ落ちて再実行で通る時は、dev の初回のコンパイル・コードを変えた直後の読み込み直しを疑い、単独で再実行してから原因を探す（KJ-2026-1005-02）。
- 生徒アプリに画面を足したら `proxy.ts` の `VALID_STUDENT_ROUTES` にも足す。開いた画面が黙ってホームになる時はこれを疑う（KJ-2026-1005-02）。
- `globals.css` を変えて見た目を確かめる時は、dev のキャッシュで古い CSS のことがある（KJ-2026-0926-04）。
- Playwright の新しいタブは履歴が2件ある。「直前の画面へ戻る」型のボタンは、前の画面から移って戻る場合だけを確かめる（KJ-2026-0926-06）。
- 手元と CI で日時の結果だけが違う時は tzdata の版を比べる。夏時間の例に規則が変わった地域（ブリティッシュコロンビア・Alberta）を使わない（KJ-2026-1018-03）。

### 1-7. 仕様・実装の確かめ方

- 複数の関数名を OR で grep したら、どの行がどの名前に一致したかを個別に確かめる。画面の機能は、関数の呼び出しだけでなく import している共通のダイアログまで見る（KJ-2026-0918-01）。
- 「データが見えない」実装（RLS・RPC の絞り込み）は「画面に入れない」根拠ではない。導線が無いことと、サーバーで拒否されることを書き分ける（KJ-2026-0922-01）。
- 回数・残高を持つ業務のジャーニーは、手順ごとに合計の不変条件（予約済み＋調整中＋未予約＝契約の回数等）を確かめる（KJ-2026-1008-01）。
- 「通知しない」「送らない」は件数ではなく、届いた宛先と種別の一覧で比べる（意図した例外を明記できる。KJ-2026-1009-01）。
- 再設定リンクを経由したかは JWT では分からない。画面の挙動で確かめる（KJ-2026-0928-03）。

## 2. 事例

### 2-1. リリース・DB の反映の確認

### KJ-2026-0904-01 リリース未反映によるセッション消化数の不整合(cancel_session 2段階更新)

- **場面**: `testing/features/branches/feature-20260904-dev/live-session-data-integrity.feature`
- **事象**: セッションは `completed` なのに、契約の `used_sessions` が実際の消化数と一致しなかった。
- **原因**: `cancel_session` の更新が「状態の更新」「使用数の更新」の2段階に分かれており、関係する2つのリリースの段階（CHECK 制約の更新・新シグネチャ）のうち片方だけが未反映だった。エラーにならず部分的に成功した。
- **対処**: 2段階を適用し、使用数を実際の消化数に合わせ直した。以降は全生徒のライセンス・チケット・担当枠・セッションの整合を確かめてから完了とした。
- **教訓**: 複数段階の RPC の部分的な未反映は「成功しているのに数が合わない」形で現れる。集計値と状態の実件数を突き合わせる。CHECK 制約の変更は RPC の存在確認では分からないため、意図した値での更新が通るかも軽く確かめる。

### KJ-2026-0917-01 内部で呼ぶ関数の未反映は、外側の RPC の preflight では見つからない（dev・staging の両方で発生）

- **場面**: `feature-20260911-dev/coach-no-show-resolution-verify.ts`（dev）、`session-lifecycle-refactor-verify.ts` ほか（staging）
- **事象**: preflight が通った RPC が、内部で `PERFORM` する `fn_consume_session_ticket`（dev）・`fn_cancel_future_sessions`（staging）が無いために `does not exist` で失敗した。dev は正常、staging だけ欠けていた関数もあった。
- **原因**: リリーススクリプトの一部の関数だけが環境に流れていなかった。外側の RPC の存在確認は、内部で呼ぶ関数の有無を見ない。
- **対処**: 利用者に報告して適用してもらった（DDL の再適用はテストから行わない）。同じ関数に依存する他のシナリオは「既知の原因による失敗」として一括で報告した。
- **教訓**: preflight の確認の対象に、RPC の中で呼ぶ関数（`PERFORM public.xxx(`）も加える。内部専用の関数も service_role からなら `.rpc()` で疎通を確かめられる。チケットを消費する正常完了の経路を避けたテストでは、この欠落に最後まで気づけない。

### KJ-2026-0924-01 staging に残っていた過去のテストデータが、新しい制約を追加するリリースを止めた

- **場面**: `supabase/release/20260919_feature-20260918-dev_release.sql` セクション5（有効なライセンスの期間の重なりの排他制約）を staging に適用
- **事象**: 事前チェックで「期間が重なる有効なライセンスが5組」と検出され、リリースが止まった。すべて過去の staging 検証の使い捨ての生徒だった。
- **原因**: シードがアプリの重複チェックを通さず、service_role で直接 INSERT していた。
- **対処**: 各生徒の最初の1件を残し、他を無効にしてから再開した。
- **教訓**: 直接 INSERT するシードも業務ルールに従う。既存データを確かめてから制約を足すセクションは、本番の適用の前に同じ条件の読み取りで本番のデータを確かめる。

### KJ-2026-0924-04 run.mjsで「記録のみ（--mark-applied）」にしたセクションが、devには実際には反映されていなかった

- **場面**: `feature-20260918-dev/student-scoped-contents-verify.ts`（dev）
- **事象**: 削除済みのはずの CHECK 制約の違反（23514）が出た。`run.mjs --status` ではそのセクションが「適用済み（記録のみ）」だった。
- **原因**: `run.mjs` の導入時に dev の既存セクションを `--mark-applied=all` で一括記録したが、そのセクションは実際には流れていなかった。
- **対処**: 冪等なセクションだったため `--reapply` で再適用し、カタログで制約が消えたことを確かめた。
- **教訓**: 「記録のみ」は反映の証明ではない。`--mark-applied` は、全セクションを適用し終えたことを各セクションの代表的なオブジェクトで確かめた環境でだけ使う。

### 2-2. DB の関数・制約の落とし穴

### KJ-2026-0914-01 部分一意インデックスに変えた後、ON CONFLICT が常に失敗していた

- **場面**: `feature-20260911-dev/session-lifecycle-refactor-seed.ts`
- **事象**: preflight は通ったが、`admin_match_student_with_coach`（内部で `fn_generate_sessions_for_schedule`）が `42P10` で必ず失敗した。
- **原因**: 一意インデックスを `WHERE status = 1` の部分インデックスに変えた際、`ON CONFLICT (schedule_id, start_datetime)` に同じ WHERE を付け忘れた。部分インデックスを `ON CONFLICT` の対象にするには INSERT 側にも同じ WHERE が要る。その後どのテストもセッションの生成を通しておらず、しばらく気づかなかった。
- **教訓**: 部分インデックスへの変更では、それを使う `ON CONFLICT` を全て探して WHERE を合わせる。しばらく通していない経路をテストで通すと、無関係な既存の不具合が見つかることがある（無視せず報告する）。

### KJ-2026-0917-05 PL/pgSQLのPERFORM(位置引数)では、整数リテラルがsmallintパラメータへ暗黙変換されない

- **場面**: `release_lesson_schedule_slot`・`invalidate_user_license`（内部で `fn_cancel_future_sessions(uuid, uuid, smallint, text)` を呼ぶ）
- **事象**: `fn_cancel_future_sessions` を反映した後も、内部の呼び出しが `function ...(uuid, unknown, integer, unknown) does not exist` で失敗した。直接呼ぶと成功した。SQL エディタで直接実行しても同じで、プーラーの問題ではなかった。
- **原因**: 引数の裸の整数リテラル（`5`）は integer に確定し、integer→smallint は関数の引数の解決では自動で変換されない（代入時だけ）。NULL・文字列リテラルは型が未確定のため問題にならない。
- **対処**: `5::smallint` と明示した。
- **教訓**: int4 以外の数値型の引数へリテラルを渡す時は常にキャストを書く。PostgREST の名前付き引数での preflight ではこの不具合は分からない。

### KJ-2026-0930-04 ビューに列を足すと、そのビューを戻り値にしている RPC（RETURNS SETOF ビュー）が実行時エラーになる

- **場面**: 生徒のモニター画面「受講生サマリー」が常に0件になった
- **事象**: `get_monitor_user_list` が `structure of query does not match function result type` で失敗していた。サーバーアクションが失敗時に空配列を返すため、画面は「0件」に見えた。
- **原因**: アドミン用にビューの末尾へ列を足した。そのビューを `RETURNS SETOF` にしていた関数の列数が合わなくなった。`CREATE OR REPLACE VIEW` はエラーにならず、関数も作り直されないため、リリースでは気づけない。
- **教訓**: ビューの列を増減したら `grep -rn "SETOF <スキーマ>.<ビュー名>" supabase/DDL` で関数を探して呼ぶ。一覧が0件の不具合は、まず RPC を実際のロールの JWT で直接呼び、エラーが空配列に化けていないかを確かめる。

### KJ-2026-1010-01 例外を返す直前の UPDATE は取り消されるため、「期限切れへ更新してから拒否」は状態が残らない

- **場面**: E2E `tests/booking/live-session-branches.spec.ts`「回答期限を過ぎた振替候補…」（dev）
- **事象**: 仕様書は「期限切れの承諾はエラー。裏で status が expired になる」としていたが、status は回答待ちのままだった。
- **原因**: `approve_slot_proposal` は `UPDATE … SET status = 5` の直後に `RAISE EXCEPTION` する。関数は1つのトランザクションのため、例外で UPDATE も取り消される。
- **対処**: 一覧・「調整中」の数え方は `expires_at` で判定しているため実害は無い。仕様書を実際の動きに直し、テストは現状を固定した。使われない UPDATE の扱いは未定。
- **教訓**: 「状態を更新してからエラー」の記述は、例外で取り消されないかを確かめる。状態の列を業務の判定に使う箇所が増える前に直す。

### 2-3. テストデータの作り方

- **原因**: (1) 複数の関数名を OR で grep し、どの名前に一致したかを確かめずに判断した（実際は取り下げの関数に一致していた）。(2) 訂正の時も関数の呼び出しだけを見て、そのファイルが import している共通のダイアログ（`SessionActionDialog`・`BookMakeupSessionDialog`。カレンダーと同じ操作一式）を見なかった。
- **教訓**: OR の grep は一致した名前ごとに確かめる。画面の機能は import 文全体（特に共通のダイアログ）まで見る。同じ箇所を2回続けて直すのは、確認の方法自体が甘い兆候。

### KJ-2026-0922-01 生徒モニタリング画面のアクセス制御主体を、RPCのデータ絞り込みと取り違えていた

- **場面**: `docs/screens/student/monitor.md`（`testing/e2e/specs/monitoring/student-monitor-dashboard.md` の作成のための確認中）
- **事象**: 画面仕様書が「閲覧権限の無い受講生には、RPC がクライアント単位で絞り込むため表示されない」と書いていた。実際に画面への入室を止めているのは `apps/student/proxy.ts`（モニターのロールが無ければリダイレクト）とダッシュボードの導線の出し分けだった。
- **原因**: RPC の `get_jwt_client_id()` による絞り込みを見て、アクセス制御が RPC で完結していると早合点し、ルーティングの守りを確かめなかった。
- **対処**: 画面仕様書を実際の守りに直し、E2E 仕様書に「モニターのロールの無い生徒の直接の URL は拒否される」異常系を書いた。
- **教訓**: データ層の絞り込みは「画面に入れない」根拠ではない。同じクライアントの別のロールが URL を直接開いた場合を、ルーティング層（proxy）で確かめる。権限の仕様書では「導線が無い」と「サーバーで拒否される」を書き分ける。

### KJ-2026-1008-01 ジャーニーのE2Eを書くと、画面ごとのテストでは見えない回数の食い違いが見つかる

- **場面**: E2E `tests/journeys/live-session-reschedule.spec.ts`（dev, 2026-10-08）
- **事象**: キャンセル時に振替候補を出した後も「未予約1回」の表示のまま予約リクエストの案内が出た。両方を承認すると、契約の回数（12回）を超えて13回目が予約された。
- **原因**: 「調整中」と予約リクエストの空き回数が、生徒が出した振替候補を差し引いていなかった。どちらの画面も単独では正しく見えた。
- **対処**: 予約できる回数を `fn_schedule_bookable_count` に一本化し、承諾・承認でも未予約の回が残っていることを確かめるようにした。
- **教訓**: 回数・残高を持つ業務のジャーニーでは、手順ごとに合計の不変条件を判定点にする。

### KJ-2026-1009-01 「管理者の操作は通知しない」には、直接マッチングの挨拶のチャットという例外がある

- **場面**: E2E `tests/journeys/admin-live-session-ops.spec.ts` 手順8（dev, 2026-10-09）
- **事象**: アドミンの代理操作の後の通知が0件のはずが、生徒に `CHAT_NEW_MESSAGE` が1件あった。
- **原因**: 直接マッチングの成立時に `fn_send_matching_greeting` が新しいコーチの名義で挨拶のチャットを送る（意図した動き）。チャットの新着はチャットの登録のトリガーで通知するため、「呼び出し元が管理者なら通知しない」の対象外になる。
- **対処**: テストは届いた通知の種別と宛先の一覧で比べるようにし、仕様書に例外を書き足した。同じ調査で、代理予約・直接マッチングがコーチの空き時間を確かめていない（仕様書は「確かめる」と書いていた）ことが分かり、仕様書と画面の注記を実装に合わせた。
- **教訓**: 「通知しない」は件数ではなく宛先と種別の一覧で比べる。

### KJ-2026-0928-03 再設定リンクで確立したセッションは、Supabase 上は「otp」でしか識別できない

- **場面**: パスワード再設定の画面（`/update-password`）を再設定リンク経由に限る改修の事前の確認（dev）
- **事象**: recovery のトークンを `verifyOtp` したセッションの JWT の `amr` は `otp` で、マジックリンク（管理者の代理ログイン）と区別できなかった。未登録のメールアドレスで `auth.admin.generateLink({ type: 'recovery' })` を呼ぶと 404 になる。
- **対処**: 再設定リンクの確認をサーバーで行い、確認したセッションに紐づく署名付きの Cookie（`packages/lib/auth/recovery.ts`）で判定する形にした。パスワード忘れは、登録の有無を外から判別できないよう、未登録でも完了画面を返す。
- **教訓**: 再設定リンクの経由は画面の挙動（未確認ならフォームが出ない）で確かめる。テストは `generateLink` の `hashed_token` を `/auth/callback?token_hash=...&type=recovery` に渡して開き、固定アカウントのパスワードを変えないよう「今と同じパスワード」を送って同一パスワードのエラーで判定を通ったことを確かめる。「未登録のアドレスはエラー」を期待しない。

### KJ-2026-0930-02 スクリプトの後始末の signOut（既定: global）で、同じユーザーのブラウザ・E2Eのログイン状態が切れる

- **場面**: お気に入りの E2E で、別の端末の変更を再現するため、テスト中に固定アカウントの実 JWT でデータを書き換えた
- **事象**: スクリプトの実行後、同じアカウントのブラウザがログイン画面へ飛ばされ、保存済みのログイン状態（`e2e/.auth/*.json`）も無効になった。
- **原因**: supabase-js の `auth.signOut()` の既定は `scope: 'global'` で、そのユーザーの全セッションを失効させる。

- **教訓**: 直接 `auth.signOut()` を呼ぶ場合も `scope: 'local'` を指定する（`e2e/CONVENTIONS.md` 10章）。
