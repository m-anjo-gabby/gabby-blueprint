# データ主体テスト運用ガイド（開発者向け）

このドキュメントは、開発者がClaude Codeに「このブランチのテストをお願いしたい」と
依頼するときの書き方・進め方をまとめたものです。AIへの技術的な指示（実装ルール）は
[CONVENTIONS.md](./CONVENTIONS.md)、テスト実施で得た知見は
[TEST-JUDGEMENT-GUIDE.md](./TEST-JUDGEMENT-GUIDE.md) にまとめてあります。
こちらは「何をどう頼めばいいか」に絞った、人間向けの運用手順です。

## 全体の流れ

このプロジェクトのブランチ運用（staging→feature/xxx→staging→main）に対応させると、
テスト依頼のタイミングは2箇所あります。

```
staging
  └─ feature/xxx を作成して開発
       └─ ① featureブランチでのテスト依頼（dev環境）
            └─ 問題なければ staging へマージPR
                 └─ ② staging検証のテスト依頼（staging環境）
                      └─ 問題なければ main へマージPR（本番リリース）
```

## ① featureブランチでのテスト依頼

機能開発が一段落したら、そのブランチでの変更内容をもとにテストシナリオを作って
dev環境で実施してもらいます。**シナリオをゼロから自分で書く必要はありません**。
このブランチでの変更点（コミット履歴・diff）をClaude自身に確認させて、
そこからGherkinシナリオを起こしてもらう形で依頼できます。

### 依頼例

> feature/xxx の変更内容をもとに、データ主体テストのシナリオを作成して
> dev環境で実施してください。
> - このブランチのコミット履歴・変更差分を見て、テストすべき観点を判断してください
> - シナリオは testing/features/branches/feature-xxx/ に作成してください
> - テストデータは削除せず残してください（ブラウザでの手動確認に使うため）

補足したいことがあれば付け加えてください。例:

- 「特に○○の権限チェック（本人/コーチ/アドミン代理）を重点的に見てほしい」
- 「△△のようなエッジケース（契約なし、期限切れ契約との共存等）も含めてほしい」
- 「このRPCのシグネチャを変更したので、旧シグネチャで動いていた箇所が壊れていないか確認してほしい」

### 実例

feature/20260904-dev（ライブセッション機能）では、このブランチでの変更差分から
5パターンの生徒シナリオ（週1回契約の消化、週2回契約でのコーチ分担、コーチ交代、
契約なしの空状態、過去契約と現在契約の共存）を洗い出してもらい、
[testing/features/branches/feature-20260904-dev/](./features/branches/feature-20260904-dev/)
にGherkinシナリオ・投入スクリプト(`seed.ts`)・検証スクリプト(`verify.ts`)として
実装してもらいました。実行時に見つかったリリース未反映（DBスキーマ変更の適用漏れ）も
その場で検出でき、[TEST-JUDGEMENT-GUIDE.md](./TEST-JUDGEMENT-GUIDE.md) に知見として残っています。

## ② stagingマージ後の検証依頼

featureブランチがstagingにマージされ、リリーススクリプトも適用し終えたら、
**①と同じシナリオ**をstaging環境に対して実行してもらいます。ゼロから作り直す
必要はなく、「①で作ったシナリオをstagingでも」と頼めば済みます。

### 依頼例

> feature/xxx が staging にマージされ、リリーススクリプトも適用済みです。
> testing/features/branches/feature-xxx/ のシナリオを使って、staging環境でも
> 同じテストを実施してください。
> - dev環境で投入済みのテストデータとは衝突しないよう、新しいtagを使ってください
> - テストデータは削除せず残してください（devの結果と比較したいため）

tagは省略しても構いません（Claudeが日時等から適当な名前を付けます）が、
後から見返しやすいよう `--tag=stg0910` のように環境・日付が分かる名前を
指定しておくと管理しやすくなります。

## 固定アカウント（蓄積データ）と過去テストデータの整理

「前期のみ契約していた生徒」「先月の学習実績」のように**過去分のデータが必要なテスト**のため、
恒久的に使う固定テナント・コーチ・生徒（`qa-` で始まるアカウント）と、その契約・学習履歴を
[FIXTURES.md](./FIXTURES.md) で管理しています。3か月単位の「ターム」で契約を持ち、投入スクリプトを
再実行するたびに不足分（新しいターム）が追加され、過去分はそのまま蓄積されます。

### 依頼例

> 固定アカウントを staging に再投入してください（タームが変わったため）。

> staging に残っている過去のテストデータを整理してください（固定アカウントは残してください）。

- 使い捨てデータ（tag付き）と固定アカウントは命名で区別しているため、「固定は残して他を削除」は
  安全装置付きのスクリプトで一括で行えます（非QAデータにまたがる場合は自動で中止します）。
- 固定アカウントでブラウザ確認したい場合は、FIXTURES.md のペルソナ一覧（生徒01〜06の契約状態）を
  見て目的に合うアカウントを選んでください。

## 結果の確認・比較

検証結果は `testing/results/` にJSONとして残ります（git管理下）。
以下のように頼めば、Claudeが該当ファイルを読んで要約・比較してくれます。

> testing/results/ にある feature-xxx の結果を、dev/staging間で比較して
> 差分があれば教えてください。

> 先週実行したテスト結果と今日の結果を比較して、リグレッションが無いか
> 確認してください。

## よくある依頼パターン

- **シナリオ改善を①→①regressionへ反映してほしい**: 「今回のfeatureブランチシナリオの
  中で、他機能でも繰り返し確認すべき内容があれば testing/features/regression/ に
  一般化して反映してください」
- **再実行のみ（シナリオは変更なし）**: 「testing/features/branches/feature-xxx/ の
  シナリオを、もう一度dev環境で実行してください（tagは新しくしてください）」
- **失敗した観点の深掘り**: 「さっきの検証で不整合が出た◯◯について、原因を調べて
  TEST-JUDGEMENT-GUIDE.mdに追記してください」

## 固定アカウント・環境前提などの情報を追加・更新してほしいとき

ソースコードだけでは読み取れない前提（固定テストアカウント、テナント、コーチのタイムゾーン・
Availability、対象ブラウザ、業務上のstatus値の意味等）は、以下のファイルに集約しています。
新しい情報がある、あるいは既存の内容を変えたい場合は、そのまま伝えれば反映されます。

| 情報の種類 | 反映先 | 依頼例 |
|---|---|---|
| 固定テストアカウント・テナント・コーチペルソナ・対象ブラウザ等 | [`FIXTURES.md`](./FIXTURES.md) | 「コーチのAvailabilityを平日夜間から土日中心に変えたいので、FIXTURES.mdを更新してください」 |
| status値・24時間ルール等の共通ビジネスルール | [`e2e/specs/_GLOSSARY.md`](./e2e/specs/_GLOSSARY.md) | 「◯◯の返還ルールが12時間から24時間に変わったので、_GLOSSARY.mdを更新してください」 |
| 機能の業務フロー・異常系 | `e2e/specs/<domain>/<feature>.md` | 「◯◯機能の仕様が変わったので、該当のE2E仕様書を更新してください」 |
| 画面単位の表示・操作内容（チーム共有用） | [`../docs/screens/`](../docs/screens/_INDEX.md) | 「◯◯画面にボタンを追加したので、画面仕様書を更新してください」 |
| Playwrightの技術方針（ロケーター戦略、外部連携の検証範囲、証跡保存方針等） | [`e2e/CONVENTIONS.md`](./e2e/CONVENTIONS.md) | 「data-testidの命名規則を変えたいので、e2e/CONVENTIONS.mdを更新してください」 |
| テスト実施で見つかった気づき・失敗事例 | [`TEST-JUDGEMENT-GUIDE.md`](./TEST-JUDGEMENT-GUIDE.md) | （Claudeが調査中に自発的に記録することが多い。「今回の件をTEST-JUDGEMENT-GUIDE.mdに記録してください」と明示的に頼んでもよい） |

### 依頼のコツ

- **「どのファイルに書くか」を指定しなくてよい。** 使い分けはClaude側で判断できるため、
  「◯◯という前提を追加してほしい」とだけ伝えれば、適切なファイルを選んで反映する。
- 複数ファイルにまたがる情報（例: 新しいロール区分の追加）は、Claudeに任せれば
  `_GLOSSARY.md`・`FIXTURES.md`・`_INDEX.md`など関係する箇所をまとめて更新する。
- 情報が仮決め・要検証の段階なら、その旨を伝える（例:「まだ確定ではないが、いったんこれで
  進めたい」）。ドキュメント側にも「初期値」「仮値」等と明記されるので、後で確定情報に
  差し替えやすくなる。
- 既存の記述と矛盾する情報を伝えた場合、Claudeは古い記述を残さず上書きする
  （このプロジェクトの仕様書・カタログ類は「今の状態のみを保つ」方針のため。過去の値は
  git historyで追える）。矛盾に気づいた場合はその旨を一言添えてもらえると、他ファイルからの
  参照箇所まで含めて確認しやすい。

## 機能追加・改修に伴う仕様書の自動メンテナンス

固定アカウント等の「情報提供」とは別に、通常の機能追加・改修作業そのものからも仕様書が
自律的に精度を保てるようにしています。具体的には、Claudeが画面（`apps/*/app/**`）・RPC・
業務ルールを変更するタスクを行う際、`docs/screens/_INDEX.md`・`testing/e2e/specs/_INDEX.md`を
確認し、対応する既存の仕様書があれば同じタスク内で更新します。**都度「仕様書も直してください」
と頼む必要はありません。**

トークン消費・複雑化を防ぐため、以下は意図的に行いません。

- **対応する仕様書がまだ無い場合の新規作成**（毎回のタスクで無秩序にドキュメントが増えるのを
  防ぐため。新規ドメインの仕様書作成は、これまで通り明示的に依頼してください）
- **無関係な仕様書の見直し**（触っていない画面・機能の仕様書まで確認しに行くことはしません。
  索引ファイルとの照合のみで、関係ない仕様書本体は読みません）

作業中に、自分が変更した箇所とは無関係な既存の記述の誤り（実装との齟齬）に気づいた場合は、
その場で仕様書を修正し、[`TEST-JUDGEMENT-GUIDE.md`](./TEST-JUDGEMENT-GUIDE.md)に事象を記録します
（`booking/individual-booking-and-reschedule.md`の画面誤りを発見・修正した際の
`KJ-2026-0918-01`が実例です）。

## 注意事項

- QAテスト用アカウントの共通パスワードは `testing/.env.local`（Git管理外。雛形は
  `testing/.env.example`）の `QA_LIVE_SESSION_TEST_PASSWORD` に設定しておけば、テスト実行時に
  自動で読み込まれます。依頼のたびにチャットへ貼り付ける必要はありません。パスワードを変更した
  場合は、このファイルと固定アカウント側の両方を更新してください。
- アカウントのメールアドレス（`qa-admin@gabby-qa-test.example` 等）は機微情報ではないため、
  [FIXTURES.md](./FIXTURES.md) とスクリプト内の定数で管理しています。
- staging環境は本番相当のデータベースです。書き込みを伴うテストを依頼する際は、
  投入内容・tag・削除有無について一度確認してから進めるのが安全です。
- devで既存のテストデータ（手動検証中のもの等）がある場合は、上書き・衝突しない
  tagを使うよう明示的に伝えてください。
