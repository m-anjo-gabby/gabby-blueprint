# データ主体テスト運用ガイド（開発者向け）

このドキュメントは、開発者がClaude Codeに「このブランチのテストをお願いしたい」と
依頼するときの書き方・進め方をまとめたものです。AIへの技術的な指示（実装ルール）は
[CONVENTIONS.md](./CONVENTIONS.md)、テスト実施で得た知見は
[TEST-JUDGEMENT-GUIDE.md](./TEST-JUDGEMENT-GUIDE.md) にまとめてあります。
こちらは「何をどう頼めばいいか」に絞った、人間向けの運用手順です。

## 全体の流れ

このプロジェクトのブランチ運用（staging→feature/xxx→staging→main）に対応させると、
テスト依頼のタイミングは2箇所あります。

```
staging
  └─ feature/xxx を作成して開発
       └─ ① featureブランチでのテスト依頼（dev環境）
            └─ 問題なければ staging へマージPR
                 └─ ② staging検証のテスト依頼（staging環境）
                      └─ 問題なければ main へマージPR（本番リリース）
```

## ① featureブランチでのテスト依頼

機能開発が一段落したら、そのブランチでの変更内容をもとにテストシナリオを作って
dev環境で実施してもらいます。**シナリオをゼロから自分で書く必要はありません**。
このブランチでの変更点（コミット履歴・diff）をClaude自身に確認させて、
そこからGherkinシナリオを起こしてもらう形で依頼できます。

### 依頼例

> feature/xxx の変更内容をもとに、データ主体テストのシナリオを作成して
> dev環境で実施してください。
> - このブランチのコミット履歴・変更差分を見て、テストすべき観点を判断してください
> - シナリオは testing/features/branches/feature-xxx/ に作成してください
> - テストデータは削除せず残してください（ブラウザでの手動確認に使うため）

補足したいことがあれば付け加えてください。例:

- 「特に○○の権限チェック（本人/コーチ/アドミン代理）を重点的に見てほしい」
- 「△△のようなエッジケース（契約なし、期限切れ契約との共存等）も含めてほしい」
- 「このRPCのシグネチャを変更したので、旧シグネチャで動いていた箇所が壊れていないか確認してほしい」

### 実例

feature/20260904-dev（ライブセッション機能）では、このブランチでの変更差分から
5パターンの生徒シナリオ（週1回契約の消化、週2回契約でのコーチ分担、コーチ交代、
契約なしの空状態、過去契約と現在契約の共存）を洗い出してもらい、
[testing/features/branches/feature-20260904-dev/](./features/branches/feature-20260904-dev/)
にGherkinシナリオ・投入スクリプト(`seed.ts`)・検証スクリプト(`verify.ts`)として
実装してもらいました。実行時に見つかったリリース未反映（DBスキーマ変更の適用漏れ）も
その場で検出でき、[TEST-JUDGEMENT-GUIDE.md](./TEST-JUDGEMENT-GUIDE.md) に知見として残っています。

## ② stagingマージ後の検証依頼

featureブランチがstagingにマージされ、リリーススクリプトも適用し終えたら、
**①と同じシナリオ**をstaging環境に対して実行してもらいます。ゼロから作り直す
必要はなく、「①で作ったシナリオをstagingでも」と頼めば済みます。

### 依頼例

> feature/xxx が staging にマージされ、リリーススクリプトも適用済みです。
> testing/features/branches/feature-xxx/ のシナリオを使って、staging環境でも
> 同じテストを実施してください。
> - dev環境で投入済みのテストデータとは衝突しないよう、新しいtagを使ってください
> - テストデータは削除せず残してください（devの結果と比較したいため）

tagは省略しても構いません（Claudeが日時等から適当な名前を付けます）が、
後から見返しやすいよう `--tag=stg0910` のように環境・日付が分かる名前を
指定しておくと管理しやすくなります。

## 結果の確認・比較

検証結果は `testing/results/` にJSONとして残ります（git管理下）。
以下のように頼めば、Claudeが該当ファイルを読んで要約・比較してくれます。

> testing/results/ にある feature-xxx の結果を、dev/staging間で比較して
> 差分があれば教えてください。

> 先週実行したテスト結果と今日の結果を比較して、リグレッションが無いか
> 確認してください。

## よくある依頼パターン

- **シナリオ改善を①→①regressionへ反映してほしい**: 「今回のfeatureブランチシナリオの
  中で、他機能でも繰り返し確認すべき内容があれば testing/features/regression/ に
  一般化して反映してください」
- **再実行のみ（シナリオは変更なし）**: 「testing/features/branches/feature-xxx/ の
  シナリオを、もう一度dev環境で実行してください（tagは新しくしてください）」
- **失敗した観点の深掘り**: 「さっきの検証で不整合が出た◯◯について、原因を調べて
  TEST-JUDGEMENT-GUIDE.mdに追記してください」

## 注意事項

- QAテスト用アカウントの共通パスワードは、実行時に環境変数
  （`QA_LIVE_SESSION_TEST_PASSWORD`）で渡します。チャットに直接貼り付けず、
  手元のシェルやパスワードマネージャーから渡す運用を推奨します。
- staging環境は本番相当のデータベースです。書き込みを伴うテストを依頼する際は、
  投入内容・tag・削除有無について一度確認してから進めるのが安全です。
- devで既存のテストデータ（手動検証中のもの等）がある場合は、上書き・衝突しない
  tagを使うよう明示的に伝えてください。
