# テスト用アカウントのルールと固定アカウント・環境前提カタログ

## アカウントの種類と使い分け

テスト用アカウントは次の3種類。状態ペルソナと利用者ペルソナをまとめて**固定アカウント**と呼ぶ。

| | 状態ペルソナ | 利用者ペルソナ | 使い捨て |
|---|---|---|---|
| 例 | `qa-student-01`〜、`qa-coach-ca-01` 等（「状態ペルソナ一覧」） | `qa-p-student-01`〜、`qa-p-coach-01`〜（「利用者ペルソナ」） | `${TAG}-<用途>`（`testing/features/branches/` のシード・E2E のフィクスチャ） |
| 目的 | 契約の状態ごとの振る舞いを判定する。過去タームの契約・学習履歴が必要な検証 | 実際の利用に近い量・ばらつきで、見た目・UAT・表示速度を確かめる | 機能ごとのシナリオ、新規アカウント特有のケース、**状態を変える操作** |
| してよい操作 | 閲覧のみ | 閲覧のみ（画面の切替・絞り込み等、データを変えない操作） | 制限なし |
| 自動テストでの判定 | 件数・値まで厳密に判定してよい | 「崩れない」「エラーにならない」までにとどめる（履歴が蓄積され値が変わるため） | 厳密に判定する |
| 生存期間 | 恒久（削除しない。再投入のたびに履歴が蓄積される） | 恒久（同上） | **期限付き**（下記「使い捨てデータの後始末」） |
| メール | `qa-<role>-<seq>@gabby-qa-test.example` | `qa-p-<role>-<seq>@gabby-qa-test.example` | `${TAG}-<用途>@gabby-qa-test.example` |
| 顧客 | `【QA固定】…` | `【QA固定】ペルソナ …` | `【QAテスト】…（${TAG}）` |

### どれを使うか

上から順に判定し、最初に当てはまったものを使う。

1. **データを書き換えるか**（予約・キャンセル・チケット消化・契約や担当の変更・お気に入り登録・学習の実施等） → **使い捨て**
2. **契約状態や過去の期間で結果が決まるものを判定するか**（権限・期間判定・集計等） → **状態ペルソナ**
3. **件数の多さ・ばらつき・見た目を確かめるか**（一覧・グラフ・カレンダー・表示速度・UAT） → **利用者ペルソナ**

固定アカウントで状態を変える操作がどうしても必要な場合（固定の担当関係の上に課題を作る等）は、
テストを直列化し（E2E は `test.describe.serial`）、作成・変更した行をテストの最後に必ず元に戻す
（例: `feature-20260918-dev/dialogue-practice-verify.ts` は固定の担当関係を使い、作成した割当・進捗・履歴を最後に削除する）。
手動確認でも同じで、固定アカウントの状態を変えたら投入スクリプトの再実行等で元に戻す。

### 命名による機械的な区別

一括削除スクリプトがこの規則で対象を判定するため厳守する。
`qa-` で始まるメール・`【QA固定】`で始まる顧客は固定、それ以外の `@gabby-qa-test.example` のメール・
`【QAテスト】`で始まる顧客は使い捨て。`${TAG}` に `qa` で始まる文字列を使わないこと。
固定アカウントの所属は必ず `【QA固定】` の顧客にする（`qa-admin` は所属なし）。使い捨ての顧客に所属させると一括削除が中止される
（`TEST-JUDGEMENT-GUIDE.md` KJ-2026-1001-01）。古い使い捨てアカウントを固定アカウントに転用しない。

例外: メール受信を確かめるE2E（`e2e/support/resendInbox.ts`）の使い捨てユーザーは、実在しない宛先への送信を避けるため
Resend のテスト用アドレス `delivered+${TAG}-<用途>@resend.dev` を使う（`@gabby-qa-test.example` ではない）。
一括削除スクリプトのメール判定には掛からないが、所属顧客は `【QAテスト】認証E2E（${TAG}）` のため顧客名で判別でき、
テストの後始末で削除される。残骸は `e2e/support/authFixtures.leftovers.ts` で確認・削除する。

### 使い捨てデータの後始末

- **原則**: テストが終わったら、そのテストのスクリプト（`cleanup.ts`・E2E の後始末）で削除する。
- **残す場合**: 手動確認のために「残してほしい」と指示された場合だけ残す。残したデータの期限は**そのブランチが次の段階へマージされるまで**
  （dev のデータは staging へのマージ、staging のデータは main へのマージ）。期限を過ぎたものは、誰が作ったかを確認せずに削除してよい。
- **一括削除**: 期限切れの残骸は `purge-disposable-qa-data.sql` で一括削除する。実行前に `inventory-qa-data.ts` で残存と固定アカウントの所属を確かめ、
  dry-run（末尾を `RAISE EXCEPTION`）→本実行の順に行う。破壊的な操作のため、実行のたびに担当者の許可を得る。

## ターム（契約期間）

固定アカウントの契約・ライセンスは、2026-06-01(JST)を起点とする**3か月単位のターム**で管理する
（T0=2026-06-01〜08-31, T1=09-01〜11-30, T2=12-01〜2027-02-28, …。計算は`testing/helpers/fixture-terms.ts`）。
実行日を含むタームを「当期」とし、`seed-fixed-accounts.ts`は前期・当期・次期の不足分だけを作る。
過去タームの契約・学習履歴は削除しないため、定期的に再投入するほど「過去分」のデータが蓄積される。

- ライセンスの日付は管理画面と同じくJSTの日境界（00:00:00.000〜23:59:59.999 JST）をUTCで保存する。
- 契約はタームごとに1件（`note`が`【QA固定】<プランコード> T<n>（期間）`）。アプリのみ契約は全生徒で共用、ライブ契約は生徒01専用。
- 学習履歴は各月10日（JST）に単語ドリル・スプリント・スプリントドリルを1件ずつ（実行日より未来の月は作らない）。

## 状態ペルソナのテナント（`com_m_client`）

- クライアント名: `【QA固定】E2E/データ主体共通アカウント`（生徒・コーチはここに所属。アドミンは所属なし）
- ポップアップ検証用: `【QA固定】ポップアップ検証`（`qa-student-07` のみ所属）。テナント限定のお知らせを配信しても他の固定アカウントに影響しないよう分離している。
- 環境に共通公開の単語/スプリント教材が無い場合、学習履歴に使う限定公開教材へのアクセス権
  （`com_m_contents_access`）をこのテナントに付与する（`seed-fixed-accounts.ts`が自動で行う）。
- 汎用スプリント（教材設定 `metadata.sprint.sprint_type='0'`。dev では「Gabby NLT」）が限定公開の場合も、
  このテナントにアクセス権を付与する（`seed-fixed-accounts.ts`が自動で行う。dev は付与済み 2026-09-30）。
  問題種別×レベルを持つのは汎用スプリントだけのため、レベルに関わる画面（お気に入りのレベル絞り込み等）の
  検証に使う。付与により、固定アカウントの教材一覧に汎用スプリントが表示される。

## 利用者ペルソナ

実際の利用者に近い量・ばらつきの学習データを持つアカウント。使い方・判定の範囲・命名は「アカウントの種類と使い分け」に従う。
パスワードは状態ペルソナと共通（`QA_LIVE_SESSION_TEST_PASSWORD`）。

投入状況: dev は全員（生徒P01〜P10・コーチ3名）を投入済み（2026-10-02）。staging は未投入。

- 学習履歴は **2026-07-01（JST）から実行日の前日まで**を作る（例外: P06 は履歴なし、P07 は2026-07-31まで）。時刻はすべて JST。
- ライセンスは前期・当期（アプリのみ契約）。P06 だけは初回投入日から当期末まで。
- 到達レベルは2026-07-01時点の起点として記録し、P10 は 08-01・08-20・09-10・09-25 にレベルが上がった履歴を持つ。
- 生徒は最新の必須規約に同意済みの状態で作る（手動でログインしても同意画面を挟まない）。
- ライブ契約（P04・P05・P09）は前期・当期のタームごとに契約・ライセンス・チケットを持ち、セッションはターム初日（2026-06-01）から週ごとに作る。終了時刻を過ぎた回は担当コーチのJWTで `resolve_stale_session` を呼んで完了にする（チケット消化と履歴はアプリと同じ経路）。当期の残りは予定（scheduled）として残る。

### 投入の方針

- `seed-user-personas.ts` で投入する（基盤データの作成処理は `testing/helpers/fixture-accounts.ts` を状態ペルソナと共用）。
- 頻度・量・時間帯には毎日少しずつの揺らぎを入れる。乱数は「ペルソナID×日付」を種にするため、同じ日付には何度実行しても同じデータができる。
  再実行すると前回から前日までの不足分が足され、日次サマリーは決まった値に戻る（手動操作でずれた値も戻る）。スプリントの実施記録は開始日時で重複を判定する。
- 汎用スプリントは環境に1件あれば足りる（metadata.sprint.sprint_type='0'。dev は「Gabby NLT」）。全ペルソナの顧客にアクセス権を付与する。
- ライブの過去セッション・スケジュール・マッチングリクエスト・チャット・ダイアログ課題は service_role で直接作る（マッチングのRPCは今日以降のセッションしか作れないため）。完了処理だけはコーチのJWTでRPCを呼ぶ。チャットはメッセージの無いルームにだけ投入する。

## 対象ブラウザ・デバイス（E2E）

| OS | ブラウザ |
|---|---|
| Windows | Chrome, Edge |
| Mac | Chrome, Safari, Edge |
| モバイル（Android/iOS） | Chrome, Safari, Edge |

**Playwrightでの実行構成**（`testing/playwright.config.ts`）: PlaywrightのブラウザエンジンはChromium/Firefox/WebKitの3種類のみで、Safari = WebKitエンジンでの近似（実機Safariそのものではない。特にWindows版WebKitは音声・マイク周りの挙動が実機と異なり得る）、Edge = Chromiumと同一エンジンという扱いにする。実行時間を抑えるため（直列実行）、標準は次の2プロジェクトのみとする。

| プロジェクト | エンジン / 端末 | 実行 |
|---|---|---|
| `desktop` | Chromium / 1440×900 | 標準 |
| `mobile` | WebKit / `iPhone 15` | 標準 |
| `mobile-android` | Chromium / `Pixel 7` | 指定時のみ（`e2e:android`） |

音声（TTS/STT）の最終確認や実機に近い検証は実機で行う（必要になればBrowserStack等の実機クラウド併用を検討する）。
