# E2Eテスト運用ガイド（機能仕様書 + Playwright）

このディレクトリは、Playwrightを使ったE2Eテスト（画面操作を通じた業務フロー検証）のための
機能仕様書置き場である。`testing/features/`（RPCレベルのデータ主体テスト・回帰テスト）とは
目的が異なる。両者の役割分担は以下の通り。

| | `testing/features/`（データ主体テスト） | `testing/e2e/`（本ディレクトリ） |
|---|---|---|
| 検証対象 | RPC・DB整合性 | 画面操作を通じたユーザーフロー |
| 実行手段 | Supabaseクライアント直叩き（tsx） | Playwright（ブラウザ操作） |
| 主な用途 | リリース前のデータ整合性確認 | UI退行の検出、業務フローの回帰確認 |

固定テストアカウント・テナント・コーチのタイムゾーン/Availability・対象ブラウザ等、
両方から共通で使う前提は[`../FIXTURES.md`](../FIXTURES.md)に集約している。仕様書の
「前提条件」節で特定のロールが必要な場合は、まずそこに使えるアカウントが無いか確認する。

実行手段は異なるが、業務フロー・異常系の「何を検証すべきか」は共通することが多い。
`specs/`配下の各仕様書（特に「異常系・バリデーション一覧」）は、`testing/features/`側の
Gherkinシナリオを起こす際の元ネタとしても使ってよい。ただし「異常系・バリデーション一覧」の
「発生層」列がRPCを含まない（UIのみ）行は、RPC直叩きのデータ主体テストでは再現できない点に
注意する。両方から参照される一次情報源という位置づけのため、下記の運用ルールはより厳格に
守ること（片方だけ更新して乖離させない）。

## ディレクトリ構成

```
testing/e2e/
├── README.md            # 本ファイル（仕様書の運用ルール）
├── CONVENTIONS.md        # Playwrightの技術規約（ロケーター戦略、外部連携の検証範囲等）
├── specs/                # 機能（ドメイン）仕様書。1ドメイン内で完結する業務フロー
│   ├── _INDEX.md         # 索引（どのspecに何が書いてあるか。まずここを見る）
│   ├── _TEMPLATE.md      # 新規仕様書のひな形
│   ├── _GLOSSARY.md      # status値・共通用語（各仕様書から参照、重複記述しない）
│   └── <domain>/
│       └── <feature>.md
├── journeys/             # ジャーニー仕様書。複数ドメインを横断する重要業務フロー
│   ├── _INDEX.md
│   ├── _TEMPLATE.md
│   └── <journey>.md
└── tests/                # （未整備）Playwrightのテストコード本体。着手時に追加する
```

`specs/`配下は機能（ユースケース）単位でファイルを分割する。1画面に閉じないフロー
（例: 生徒がリクエストしコーチが承認する、といった複数画面・複数ロールをまたぐ操作）が
中心となるため、画面単位ではなく機能単位を基本とする。ボタン文言・レイアウト等の
画面固有の詳細はここでは扱わず、[`../../docs/screens/`](../../docs/screens/_INDEX.md)の
画面仕様書（チーム共有用、実装に詳しくない読者も想定）にリンクする。該当する画面仕様書が
まだ無い場合は、実装（該当コンポーネント）を直接参照する。

存在するドメイン・未着手ドメインの一覧は[`_INDEX.md`](./specs/_INDEX.md)を参照
（README側には重複して書かない）。

### ジャーニー仕様書（journeys/）との使い分け

`specs/<domain>/`は1つの機能ドメイン内で完結する業務フローを扱う。一方、新規顧客の利用開始
フローのように、顧客・契約管理〜生徒登録〜アクティベーション〜マッチング〜自主トレーニング
といった**複数ドメインを横断し、かつリグレッション上最優先で守るべきフロー**は、`specs/`の
粒度に無理に収めず`journeys/`に置く。

- ジャーニー仕様書はステップの並びと「どのドメイン仕様書・画面仕様書を参照すべきか」だけを
  書く。異常系・画面詳細・RPCのパラメータ等は書かず、各ドメイン仕様書に譲る（重複させない）。
- 参照先の仕様書がまだ無いステップは「未整備」と明記する。この「未整備」の集まりが、次に
  作るべきドメイン仕様書の優先順位そのものになる（`journeys/<journey>.md`の「未整備の依存
  ドメイン」節を参照）。
- 運用ルール（現状のみ記述、索引更新、気づきはTEST-JUDGEMENT-GUIDE.mdへ等）は`specs/`と共通。

## 仕様書の運用ルール（肥大化・陳腐化を防ぐための最重要ルール）

1. **「今の仕様」だけを書く。変更履歴・経緯は書かない。**
   `supabase/release/*.sql`のような「なぜこう変わったか」の蓄積はこの仕様書の役割ではない
   （経緯を知りたい場合はgit historyやSQLコメント側を見る）。仕様変更時は該当箇所を
   **上書き**し、追記でバージョンを積み増さない。
2. **1ファイルが大きくなったらサブフロー単位で分割する。**
   目安として、正常フローが複数の独立した分岐（例: 個別予約と振替候補提案）を持ち、
   互いの異常系・テストケースが混ざって読みにくくなってきたら分割する。
3. **共通用語はGLOSSARY.mdに集約し、各ファイルはリンクのみ。**
   status値の意味などをファイルごとに書くと、値の意味が変わった際に全ファイルを
   直す羽目になる。唯一の真実源をGLOSSARYに置く。
4. **実装（RPCシグネチャ・サーバーアクション名）を変更したら、同じPR内で該当仕様書も更新する。**
   仕様書と実装が乖離すると、Claudeが古い仕様書を根拠に誤ったテストを書く原因になる。
5. **Claudeは対象タスクに関係するファイルのみを読み込む。** 全件を先読みする必要はない
   （`specs/`全体をコンテキストに載せるのではなく、まず`_INDEX.md`で該当specを特定し、
   扱う機能のファイル1〜2個だけを読む）。
6. **新規specを追加・大幅変更したら`_INDEX.md`も更新する。** 索引が古いと「関係specを
   探すのに結局全ファイルを開く」羽目になり、索引を置く意味が無くなる。
7. **仕様書を使った作業中に見つけた「実装との齟齬」「非自明な挙動」は、仕様書ではなく
   [`testing/TEST-JUDGEMENT-GUIDE.md`](../TEST-JUDGEMENT-GUIDE.md)に記録する。**
   仕様書は現状のみを保つ方針（ルール1）のため、気づきの蓄積先はデータ主体テストと
   共通のこのファイルに一本化する。蓄積内容のうち恒久的に反映すべきものは、次に該当
   仕様書を更新するタイミングで反映する。

### 「異常系・バリデーション一覧」の発生層列

各仕様書の「異常系・バリデーション一覧」表には、検証がどの層で行われるかを示す
「発生層」列を必ず設ける。値は以下の3種類。

| 値 | 意味 |
|---|---|
| UI | クライアント側のみの検証（入力制限・警告表示等）。サーバー側では強制されない |
| RPC | サーバー側（SECURITY DEFINER関数）での検証のみ。UI側に導線が無い場合は「RPC（UI導線なし）」と注記する |
| 両方 | UI側の事前チェック（参考表示・送信抑止等）とRPC側の最終検証の両方がある |

この列がある理由は、Playwright（画面操作）とデータ主体テスト（RPC直叩き）のどちらで
検証できるかが層によって変わるため。「UI」のみの行はデータ主体テストでは再現できず、
「RPC（UI導線なし）」の行はPlaywrightでは再現できない。表を作る時点でこれを明示しておくと、
テストケース化の際にどちらの手段を使うべきか迷わない。

## 新規仕様書の作成

`specs/_TEMPLATE.md`をコピーし、該当ドメインディレクトリに機能名で保存する。
各セクションの意図は`_TEMPLATE.md`内のコメントを参照。

## Playwright環境について

本リポジトリには現時点でPlaywrightは未導入。`specs/`の整備が一段落し、実際に
テストコードを書く段階になったら、`testing/tests/`（本パッケージ）にdevDependencyとして
追加し、ロール別（student/coach/admin）に`storageState`でログイン済みセッションを
保存する方式を想定している（認証情報の扱いは`testing/CONVENTIONS.md`の方針を踏襲する）。

ロケーター戦略・外部サービス依存機能の検証範囲・失敗時証跡の保存方針等、Playwright導入前に
決めておいた技術方針は[`CONVENTIONS.md`](./CONVENTIONS.md)にまとめてある。着手時はまず
そちらを参照する。
