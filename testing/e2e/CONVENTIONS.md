# E2Eテスト技術規約（Playwright）

## 1. ロケーター戦略（ハイブリッド）

- 基本はPlaywright標準のrole/textベースセレクタ（`getByRole`, `getByLabel`, `getByText`）を使う。
- 以下に該当する箇所は`data-testid`を明示的に付与する。
  - 同一構造が繰り返されるカード/リスト項目（例: `BookingRequestCard`, `RescheduleProposalRequestCard`）で、特定の1件を一意に指定する必要がある場合
  - status（pending/approved等）で見た目だけが変わり、role/textでは判別しづらい要素
  - coach appの英語文言・student/adminの日本語文言のように、アプリによって表示文言が異なり、同じテストロジックを使い回したい箇所（CLAUDE.md 5章のアプリ別UI言語方針を参照）
- `data-testid`の命名規則: `<feature>-<element>`（例: `booking-request-card-approve-button`）。ケバブケースで、長くなりすぎないようにする。
- 新規UIコンポーネント実装時に上記へ該当するかは実装者判断でよい。**先回りして全要素に付与しない**。まずrole/textで書き、テストが不安定になった箇所だけ後から`data-testid`を足す運用とする。

## 2. 外部サービス依存機能の検証範囲

業務フロー（画面遷移・入力・DB状態変化）まではE2Eで検証し、以下は対象外またはモック化する。
実サービスへの実接続を伴う検証（映像/音声品質、実メール受信確認等）は本方針の対象外とし、
必要であれば別途手動確認または専用の検証手段を用意する。

| 機能 | E2Eで検証する範囲 | 対象外・モック化する部分 |
|---|---|---|
| Zoom Video SDK（ライブセッション通話） | ルーム入室ボタンの表示・入室操作・退室後の画面遷移等 | 実際の映像/音声の疎通、通話品質 |
| Resend（メール送信） | メール送信トリガーとなる操作が成功すること（画面上の成功表示・送信履歴の記録） | 実際のメール受信・文面の見た目 |
| Azure Speech SDK（音声認識・TTS） | 音声入力UIの表示・録音開始/停止操作 | 認識精度・実際の音声合成品質 |

外部サービス呼び出しをモックする方式（APIレイヤーでスタブ化する、テスト用エンドポイントを
用意する等）は、Playwright導入時に機能ごとに実装方針を決める。本ファイルには
「どこまで見るか」の境界のみを定義する。

## 3. 固定アカウントの並列実行時の扱い

[`../FIXTURES.md`](../FIXTURES.md)の固定アカウントは複数のテストワーカーから同時に
使われる可能性があるため、以下を守る。

- 固定アカウントを使うテストは、状態を変更しない操作（閲覧・表示確認）に限定する
- 状態を変更する操作（予約、キャンセル、承認等）を検証したい場合は、都度シードしたアカウント
  （`testing/CONVENTIONS.md`の命名規則）を使う
- 上記に反してどうしても固定アカウントで状態変更操作を検証する必要がある場合は、該当テストを
  `test.describe.serial`等で直列化し、他のテストと並列実行させない

## 4. テストケース優先度の運用上の意味

各仕様書の「E2Eテストケース候補」表の優先度は、以下の実行タイミングに対応させる。

| 優先度 | 実行タイミング（想定） |
|---|---|
| 高 | 毎PR（CI） |
| 中 | リリース前（stagingマージ時等） |
| 低 | 手動確認、または不具合が疑われる時のみ実行 |

CI組み込み自体はPlaywright導入時に行うが、仕様書に優先度を書く時点からこの意味で
統一しておく。

## 5. 失敗時証跡の保存方針

- スクリーンショット・動画・trace（`.zip`）はCIのartifactとしてのみ保存し、
  リポジトリにはコミットしない（`.gitignore`対象とする）
- データ主体テストの`testing/results/`（軽量なJSON検証ログ、git管理）とは性質が異なるため
  混在させない
- 再現性のある失敗（繰り返し同じ箇所で落ちる等）は、証跡そのものではなく事象・原因を
  [`../TEST-JUDGEMENT-GUIDE.md`](../TEST-JUDGEMENT-GUIDE.md)にテキストで記録する

## 6. コードの完了条件・禁止パターン

CLAUDE.md 3章の`tsc --noEmit`/`eslint`に加えて、以下を満たすこと。

- 固定の`page.waitForTimeout()`によるスリープ待ちを使わない。web-first assertion
  （`expect(locator).toBeVisible()`等、Playwrightの自動リトライに任せる書き方）を使う
- `test.only` / `test.describe.only`をコミットに残さない
- テスト間で状態を共有しない（前のテストの実行結果に依存するテストを書かない。並列実行・
  実行順の入れ替えのどちらでも成立すること）
