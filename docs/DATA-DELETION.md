# データの削除の規約

業務データの「削除」の種類と、テーブルごとの扱い・外部キーの決め方。DB の正本は `supabase/DDL/`。

> 退会（§4）の消去の範囲は MVP として先行実装した推奨案。運営に確認して確定する（利用規約の「削除」を匿名化で満たせるか・チャットの本文を残すか）。

## 1. 削除の4種類

| 種類 | 意味 | 使う場面 | 戻せるか |
|---|---|---|---|
| **A. 使用をやめる** | `status` / `is_active` を変える。データと関係は残る | 通常の運用（顧客の取引終了・教材の非公開・プランの販売終了・ユーザーの停止） | 戻せる |
| **B. 誤登録の取り消し** | 行を物理削除する。**利用実績が1件でもあれば拒否し、A を案内する** | 登録の誤り・未使用のもの | 戻せない |
| **C. 退会（個人情報の消去）** | 本人を特定できる情報を物理削除し、業務の記録は「退会済みユーザー」として残す | 利用規約に基づく削除の申し出 | 戻せない |
| **D. 顧客単位の一括削除** | 顧客（client）に属するユーザー・契約・記録をまとめて物理削除する | テストデータ・営業用デモ・誤って作った顧客 | 戻せない |

- **論理削除（`delete_flg`）は使わない。** 「消したことにして残す」状態を作らず、残すものは意味のある状態（A）、消すものは物理削除（B〜D）にする。
- 例外: チャットのメッセージの取り消し（`com_t_chat.deleted_at`）は、画面に「削除されたメッセージ」と出す機能の状態として残す。
- **Storage のファイル**: 行を物理削除したら、その行（と `CASCADE` で一緒に消える行）が持つファイルも消す。DB の削除を先に行い
  （削除した行から `select` でパスを受け取る等）、ファイルは `removeStorageFiles()`（`packages/lib/storage/removeStorageFiles.ts`）で消す。
  ファイルの削除に失敗しても DB の削除は取り消さず、エラーのログ（`<domain>:delete_files_failed` 等）で気付けるようにする。
  他の行がまだ同じパスを使う可能性がある場合（スプリントの問題の音声等）は、使われていないパスだけを消す。
- B の「実績があれば拒否」は外部キーの `RESTRICT`（§3）を最終的な安全装置にする。サーバーアクションは `isInUseError()`（`packages/lib/supabase/pgErrors.ts`。エラーコード `23503`）で判定して `reason: 'in_use'` を返し、画面は「使われているため削除できません。〜をオフにしてください」と A を案内する。事前に件数を確かめて文言を分けてもよい（例: `deleteContract`）。
- C・D は admin の **DangerZone**（`components/common/DangerZone.tsx`。区画の最下部、赤枠）に置き、`TypedConfirmDialog`（対象の名前の入力で確認）で実行する。D は実行前に消える件数を種類ごとに表示する。実行できるのはシステム管理者（`admin` ロール）だけ（`adminDataDeletionAction.ts`）。

## 2. 列の使い分け

| 列 | 使う場面 | 型 |
|---|---|---|
| `status` | 業務の段階があるもの（ユーザー・顧客・契約・ライセンス・教材・割当） | `smallint`（値と意味は列のコメントと `packages/types` の定数に書く） |
| `is_active` | 選択肢として出すかどうかだけを切り替えるマスタ（プラン・専門分野・国・タイムゾーン） | `boolean NOT NULL DEFAULT true` |
| （無し） | 段階が無く、要らなくなったら消すもの | — |

- 1つのテーブルに `status` と `is_active` の両方を持たせない。
- 選択肢・一覧の取得は「有効なものだけ」を条件にする（admin のマスタの一覧は全件を出し、使用をやめたものに `InactiveBadge` を付ける。編集では `ActiveSwitchField` で切り替える）。**過去の記録の表示（学習履歴・セッション・レポート）は条件を付けず**、使用をやめたものの名前も出す。
- 編集中の行が使用をやめた選択肢を使っている場合は、その選択肢だけは残す（例: 契約の編集で販売終了のプラン）。

### テーブルごとの扱い

| テーブル | 状態の列 | 削除 |
|---|---|---|
| `com_m_user` | `status`（1:有効 / 0:停止 / 9:退会済み） | C。停止は認証のアカウントの ban でログインできなくする（再開で解除） |
| `com_m_client` | `status`（1:取引中 / 9:取引終了） | B（`deleteClient`。契約・ユーザーがあれば拒否）、D |
| `com_m_contents` | `status`（1:公開 / 0:非公開。新規作成時は非公開）。公開範囲は `content_scope`（0:共通 / 1:限定）で別に持つ | B（学習の履歴・割当があれば拒否） |
| `com_m_contract` / `com_t_user_license` | `status` | B（`deleteContract`。ライセンスの割当があれば拒否） |
| `com_t_dialogue_assignment` | `status`（1:割当中 / 0:解除） | 消さない（解除しても進捗・会話ログを残す） |
| `com_m_color_vowel_dictionary` | `status`（公開ステータス） | 物理 |
| `com_m_contract_plan` / `com_m_coach_specialty` / `com_m_country` / `com_m_timezone` | `is_active` | B（使われていれば拒否） |
| `com_m_sprint_questions` | — | 物理（検証・誤登録の問題の片付け用。公開中の問題は通常消さない）。回答の履歴（JSON）は問題 ID だけを持つため残り、結果画面では問題文を引けない問題を一覧から外す（点数の集計は残る）。お気に入りは一緒に消える。音声ファイル（Storage の audio）は問題の削除の後に消し（TSV の一括登録の洗い替えも同じ。他の問題が使っているパスは残す）、失敗しても削除は取り消さずにエラーのログ `sprint:delete_audio_failed` を出す |
| `com_m_calendar_event` | — （公開は `is_published`） | 物理。開催済み（開始日時を過ぎた）のイベントは削除できず、非公開にする |
| `com_m_notice` | — （公開は `is_published`） | 物理（既読も一緒に消える） |
| `com_m_dialogue_session` | — | B（進捗・会話ログがあれば拒否） |
| `com_m_calendar_event_series` / `com_m_coach_availability` / `com_m_contents_access` / `com_m_contents_tag` / `com_m_phrase` / `com_m_ai_knowledge_base` | — | 物理 |
| `com_m_color_vowel` / `com_m_role` | — | 固定のマスタ。画面からは削除しない |

## 3. 外部キーの `ON DELETE`

外部キーは全件で次のどれかを明示する（指定なし＝`NO ACTION` は使わない。リリーススクリプトの外部キーの節は、`public` スキーマに `NO ACTION` が残っていたら中断する）。

| 指定 | 使う場面 | 例 |
|---|---|---|
| `RESTRICT` | 参照元が**業務の記録**（契約・支払い・セッション・学習の履歴・顧客への報告）か、マスタの参照。親を物理削除しようとしたら止める | セッション → ユーザー・チケット・予定、チケット → ライセンス、ライセンス → 契約、学習の履歴 → 教材、契約 → プラン、ユーザー → タイムゾーン |
| `CASCADE` | 参照元が**親に付属するだけ**で、親と一緒に消えてよい | お気に入り・メール設定・タグの紐付け・イベントの参加者・教材の限定公開の設定・ダイアログのセッション明細 |
| `SET NULL` | 「誰が操作したか」「どこから来たか」を残すだけの列 | `cancelled_by`・`approved_by`・`responded_by`・`performed_by`・`rescheduled_from`・`source_request_id` |

- 業務の記録へ `CASCADE` で辿れる経路を作らない（親を1行消すと記録が連鎖して消える）。
- 生徒本人の学習の記録（`self_t_*`・`student_*`）は、ユーザーからは `CASCADE`（B・D でユーザーと一緒に消える）、教材からは `RESTRICT`。
- C（退会）では `com_m_user` の行を消さないため、`com_m_user` を参照する外部キーは C には影響しない。B と D で効く。
- `com_m_user.id` は `auth.users(id)` を参照しない（退会で認証のアカウントを消したあとも、退会済みの行を残すため）。ユーザーの作成は認証のアカウントの作成（`handle_new_user`）からだけ行う。

## 4. 退会（C）

`fn_withdraw_user`（SECURITY DEFINER、service_role 専用、1トランザクション）で DB を処理し、続けてサーバーアクション `withdrawUser` が Storage のファイルと認証のアカウントを消す。途中で失敗しても、もう一度実行すれば続きから終わる（退会済みのユーザーにも同じ削除を行う）。画面は admin のユーザー詳細の「アカウントの操作」。

**先に済ませること**（残っていれば中断する）: 有効なライセンスの停止、今後のセッションのキャンセル、回答待ちの申請・稼働中の定期予定の終了。取り消しの通知・チケットの返還は既存の画面に任せる。

| データ | 扱い |
|---|---|
| `com_m_user` | 行は残す。`status = 9`、`user_name` を「退会済みユーザー」、`icon_path` を NULL。`timezone` は過去の記録の日付の計算に使うため残す |
| 認証のアカウント（`auth.users`） | 削除。メールアドレス・ログインの情報が消える |
| 正式氏名・お気に入り・途中再開の状態・メール設定・通知・ロール・未使用の招待 | 削除 |
| メールの送信記録（`com_t_mail_outbox`）と配信の記録（`com_t_mail_event`） | 削除（宛先のメールアドレスを含むため） |
| 生徒について書かれた情報（コーチのメモ・宿題とその添付） | 削除 |
| コーチのプロフィール・空き時間・専門・マッチングの停止設定 | 削除 |
| プロフィール画像・紹介ビデオ・宿題の添付（Storage） | 削除 |
| Webトライアルの申込 | 氏名・メールアドレス・国と都市を消す。要望・知ったきっかけ・職業はマーケティングのため残す |
| チャット・セッション内のチャットの本文と添付 | **残す**（送信者は「退会済みユーザー」と表示。必要なら admin がルームを削除する） |
| セッション・チケット・ライセンス・契約・評価の点数・研修レポート・学習の記録・イベントの参加の記録・規約への同意の記録 | 残す（匿名の実績） |
| 削除の記録 | `com_t_data_deletion_log` に種類・対象の ID・消した件数・実行者・日時を残す（氏名・メールアドレスは含めない） |

- 退会済みのユーザーは、代理ログイン・停止・再開の対象外。admin のユーザー一覧には「退会済み」として残る（`vw_user_list.user_status`）。
- 顧客のモニター画面（`get_monitor_*`）には退会済みの生徒を出さない（顧客の担当者が見る画面のため、退会した人の情報は見せない。
  認証のアカウントとの内部結合で外れる）。
- 同じメールアドレスでの再登録は、新しいユーザーとして扱う。

## 5. 顧客単位の一括削除（D）

- `fn_purge_client`（SECURITY DEFINER、service_role 専用）。顧客に属するユーザーと、その評価・研修レポート・セッション・予定・マッチング・担当関係・チケット・ライセンス・契約・招待を `RESTRICT` に当たらない順に消し、ユーザー（付属するデータは `CASCADE`）と顧客（お知らせ・イベント・教材の限定公開の設定は `CASCADE`）を消す。参加者がいなくなったチャットルームも消す。認証のアカウントと Storage のファイルはサーバーアクション `purgeClient` が消す。
- `p_dry_run = true` の予行で種類ごとの件数を返す（何も消さない）。画面（admin の顧客の編集ダイアログの最下部）は開いた時に予行の件数を見せ、顧客名の入力で確認してから実行する。
- **削除できない顧客**: 初期テナント（`client_type = 0`）・Webトライアルの固定の顧客・管理者が所属する顧客・他の顧客のユーザーとの業務の記録がある顧客（例: この顧客のコーチが他の顧客の生徒を担当している）。
- 共通の教材など、他の顧客と共有しているものは消さない。

## 6. 自動の削除

| 対象 | 扱い |
|---|---|
| Webトライアルの申込 | 本登録の有無にかかわらず残す（要望・知ったきっかけをマーケティングに使う。自動の削除は保留） |
| メールの送信記録・cron の実行記録 | 既存の `mail-history-purge-daily`・`cron-run-history-purge-daily` が古いものを消す |

## 7. 新しいテーブル・画面を作るとき

1. 「残す必要があるか」から決める。段階があれば `status`、選択肢の出し分けだけなら `is_active`、どちらでもなければ列を持たない（§2）。
2. 外部キーは §3 のどれかを必ず書く。業務の記録なら `RESTRICT`。
3. 個人情報を持つテーブルは、退会（`fn_withdraw_user`）で消すか残すかを決め、関数と §4 の表を同じタスクで直す。顧客に属するデータは、一括削除（`fn_purge_client`）の順序に入るか確かめる（`RESTRICT` の参照を増やしたら、関数で先に消す）。
4. 画面の「削除」は B（実績があれば拒否して A を案内）にする。戻せない操作を足す場合は DangerZone に置く。
